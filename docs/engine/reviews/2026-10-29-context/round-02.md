### 一、 撤回不成立推论与重定事实基线

首先明确撤回上一轮中越界的推论：
1. **撤回对 73904 字符成因的误判**：已知原文已有 400/120 字符节选、失效旧回答已替换为 `changed` 占位，73KB 并非长原文倾倒，而是**每条命中消息各自附带了完整的修订解释导致的重复膨胀**。

### 二、 材料的四层边界：模型需要看什么 vs 宿主验证什么？

同一份材料包含四类信息，按“模型推理必需”与“宿主机器核查”严格切分：

| 信息层级 | 谁需要处理 | 为什么 / 最小展示要求 |
| :--- | :--- | :--- |
| **1. 正文节选**（事实/报告/假设/changed占位） | **模型必看** | 推理的原始语义材料。 |
| **2. 已知纠正与状态性质**（supported / withdrawn / conditional / ambiguous / 身份缺口） | **模型必看** | 决定正文的置信度与认识边界，缺一不可。 |
| **3. 引用定位与有效范围**（Span / 作用区间 / 局部语境） | **模型必看（语义级）** | **防范围污染的关键**。模型不需要看字节偏移量（如 `byte_offset: 1042-1180`），但必须看到**锚定文本或局部指向**（如“仅针对‘正门可推车’这一句”或具体时间段），否则会把局部 `withdrawn` 误认为整段作废，或把 `conditional` 当成全局确定。 |
| **4. 机器核查元数据**（SHA256 stateHash / sourceHash / 冗长 UUID / 内部审计路径） | **仅宿主验证** | 64位十六进制哈希是给宿主做 `==` 比较防篡改用的。模型无法对哈希做密码学验证，它只需要**区分同一会话内的不同来源与不同版本**。在失败页中，源 hash/片段映射占 9741 字节、来源元数据占 5694 字节（合占页头近 70%），这是纯粹的机器载荷遮蔽了业务语义。 |

**如何保证不把不确定变确定、不混淆局部与整体？**
压缩的底线是**保持二分图（Bipartite Graph）拓扑与状态标签严格同构**：只压缩节点 ID（哈希变短句柄）和消除同一工具调用内的重复节点，绝不合并或省略边上的 `span` 语义限定词与 `status` 属性。

### 三、 局部修正方案对比与可执行不变量

不预设大改架构，针对您提出的几个极小切口进行边界与副作用分析：

#### 切口 1：在单次 `recall` 内部做批量修订说明（消除同次调用的逐命中重复）
* **能解决多少**：直接打掉初始 `recall` 从几千字正文膨胀到 `73904` 字符的根因（8个命中共享同一批依赖时，无需重复打印8次修订表）。这能使大量原本健康的 `recall` 直接落在 `12000` 字符阈值之内，**从源头避免触发 `context_read` 引用转换和后续分页**。
* **可能造成什么失败**：在单次 `recall` 内部，如果把逐条附带的修订移到该 `recall` 结果的尾部/头部汇总，模型必须通过引用标记（如 `[msg_3 -> src_A]`）做跨段对齐。若标记设计不直观，弱模型（如 Flash LOW）可能发生张冠李戴。

#### 切口 2：机器哈希/UUID 映射为本次稳定短句柄（如 `S1@v2`, `N3`）
* **能解决多少**：直接针对 `9741 + 5694 = 15435` 字节的机器元数据大头。将 64 字节 Hash + 冗长元数据键名映射为紧凑短句柄（宿主在内存维护双射表以备审计），无需改变任何上下文生命周期，单页页头即可缩减约 40%~50% 字节。
* **可能造成什么失败**：如果短句柄在同一次会话的不同轮次间发生重编号（如上一轮 `S1` 是茶清单，下一轮 `S1` 变成书屋通知），当历史工具结果还在上下文中时，会造成严重的**跨轮指代污染**。
* **必要不变量**：短句柄必须在**整个上下文生命周期内单调分配或基于 Hash 前缀确定性生成**，绝不重用。

#### 切口 3：修改 `>12000` 转引用的判定边界与分页结构
当前痛点是“正文仅几百字，因修订头 22KB 超过 12000 阈值，迫使正文变成 `context_read` 引用，逼迫模型再去分页读一遍同样的 22KB 修订头”。对比两种最小边界：

* **方案 I：正文与修订分开计长，且仅对超长正文分页（推荐的最小直接方向）**
  * **机制**：工具结果依然自包含（维持 `atomic`），但 `>12000` 转 `context_read` 的阈值**仅计算“正文节选”长度**。如果 8 条命中的正文只有 4000 字符，即使附带了 15KB 的当前修订头，也**直接一次性展示正文+修订头**，不转成 `context_read` 引用！只有当正文自身超过阈值时才对正文分页。
  * **收益与代价**：**零生命周期风险**（不破坏现有的单工具结果自足与淘汰边界）。直接消灭了“为了读 3000 字正文而额外多触发一次携带 22KB 重复页头的 `context_read`”的荒谬循环。代价是单次工具消息可能达到 19KB，但在窗口允许时，1 次 19KB 远优于“22KB 引用 + 25KB 分页 = 47KB”。
* **方案 II：请求级共享状态表（剥离工具内修订）**
  * **生命周期与淘汰边界**：若工具结果只留正文，修订移至请求级共享表，当上下文管理器**摘要或淘汰旧工具组**时，或者**后续轮次某来源发生新变化**时，极易破坏自足性。
  * **必须满足的可执行不变量（Garbage Collection & Pinning Invariant）**：
    1. **引用计数绑定**：只要上下文中任何留存的消息（含未被淘汰的工具正文、或生成的对话摘要）引用了来源集合 $S_{active}$，共享状态表中对应 $S_{active}$ 的最新修订就**不可被裁剪**。
    2. **摘要同步失效**：当旧对话被压缩成摘要时，摘要节点必须继承被压缩工具组的 `source_id` 集合；一旦宿主检测到该集合中某来源在后续轮次有了新 `stateHash`，宿主必须在共享表中高亮更新，或在摘要旁注入 `changed` 警告，否则模型就会“只记住旧摘要里的事实而漏掉新纠正”。
  * **判断**：方案 II 涉及复杂的跨轮状态垃圾回收不变量，作为下一步最小修正，**工程复杂度过高，不如【切口 1 + 切口 2 + 方案 I】直接且安全**。
