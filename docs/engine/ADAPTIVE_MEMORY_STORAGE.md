# 自适应记忆：结果发布与恢复协议

状态：M1 工程协议已实现，语义处理器尚未接入；M1 整体放行以阶段验证记录为准。目标和边界见[实施计划](ADAPTIVE_MEMORY_PLAN.md)、[行为契约](ADAPTIVE_MEMORY_CONTRACT.md)与[验证记录](ADAPTIVE_MEMORY_PROGRESS.md)。

## 1. 权威边界

- 原始发言和消息状态仍在既有 SQLite；不为本协议复制完整对话到灵魂 Git。
- 未交付的生成结果存于同一 SQLite 的持久发件箱；任务完成与结果入箱同事务，不依赖模型再次生成来恢复。
- 完整结果文件位于私有灵魂 `notes/QuetzalMemory/Adaptive/<任务 UUID>.md`。文件是处理结果存档，不是事实确认；后续语义认识及其修订由有版本的 payload 表达。
- Git 是文件的版本历史；SQLite 的发布状态是恢复回执。索引和图仍为派生视图。文件落盘、本地 Git 提交、远端同步、语义可用是四种不同状态。

路径符合灵魂规范 v14 的既有 Markdown 笔记目录，不增加顶层目录、不改变固定文件格式，因此不提升灵魂规范版本。SQLite 自适应表从 schema 1 原子升级为 2；未知版本或不同 agent 拒绝打开。旧程序降级与备份恢复仍须 M4 单独验收，不能假定旧读取器认识本协议。

## 2. 最小传输信封

Markdown 内使用单行 JSON 代码块，包含：

| 字段 | 含义 |
|---|---|
| `format` | 固定 `quetzal-adaptive-result-v1`，未知版本拒绝解析 |
| `id` | 创建该结果的任务 UUID v4；也是不可变文件名 |
| `agent` | 所属灵魂身份；必须与当前 agent 一致 |
| `processor` | 处理器版本，如测试处理器；不表示可信级别 |
| `createdAt` | 中心接受结果的时间；不代替事件发生时间 |
| `inputs` | 1～100 个不重复来源引用 `{id, revision, hash}` |
| `payload` | `{schema, data}`；语义处理器自己校验具体 schema |

整个 JSON 至多 256 KiB，来源 hash 为完整快照 SHA-256。`revision` 是中心本机来源版本，不是跨身体统一计数；重建或跨身体匹配必须以 agent、来源 ID 和 hash 核对，不能拿不同数据库的 revision 作全局先后比较。M2 阶段内已有 [semantic-v1 格式与依赖计算库](ADAPTIVE_MEMORY_SEMANTICS.md)，尚未接入后台和查询；未知 payload 只能检查存档，不能进入上下文。

同一任务只接受一次结果。修改认识应产生后续结果并保留依赖及修订关系，不覆盖旧文件；semantic-v1 库已实现记录修订与旧版本依赖失效，模型纠正理解尚未接通；权威文件重建已有内部库与合成恢复测试，宿主生命周期仍待接线。

## 3. 四个持久阶段

1. **接受结果。** 在 `BEGIN IMMEDIATE` 内检查任务租约令牌、未取消、租约未过期、主要来源版本与全部输入的版本 / hash；结果入 `adaptive_publications`，处理回执与任务 done 一起提交。可信宿主可提供语义投影安装器，与上述写入同事务；返回拒绝或抛异常均回滚全部写入。任一步失败整体回滚。完成回执只说明处理过，不确认正文为真。
2. **安装文件。** 固定主机在后台、灵魂写锁内运行；写同目录随机 `.tmp`，flush 文件，再以不可替换的硬链接原子安装最终名，删除临时名并 flush 目录。同名相同内容只补回执，不重写；同名不同内容、父目录链接、非法文件或摘要不符拒绝覆盖。
3. **记录文件完成。** 发件箱 `pending → written`。此时文件完整，但还不能宣称进入版本历史；文件写入失败每 30 秒重试，最多 5 次，冲突立即失败。只保存错误代码，不保存可能带正文的异常信息。
4. **确认本地 Git。** 复用基座的灵魂提交 / 同步入口，再逐个读取 `HEAD:<路径>`，只有与发件箱预期文件完全一致才 `written → published`。Git 失败保留 written，30 秒后补做，最多 5 次转 failed。重启继续这个阶段，不重新调用生成器。

宿主每轮最多安装 5 份、提交确认 5 份，分别检查启用状态、固定主机身份和急停。Git 异步执行，不在前台查询等待；文件安装仍为同步磁盘操作，其负载与延迟须另测。关闭或急停后不启动下一发布阶段；已进入 Git 的操作不假装可以回滚或立即中断。

`memory.adaptive.status` 的 `queue.publications` 返回 pending / written / published / failed 数量；语义任务 done 可以同时有 pending 或 written 的交付记录，不能据 done 判断持久化全部完成。目前没有发布失败的 UI 重试入口，属于 M4 运维待办；不通过无限重试掩盖失败。

本地 published 不证明远端已同步。远端仍由现有灵魂同步机制负责，状态见既有同步界面；跨重启后的远端恢复与完整备份必须分别验收。原有同步故障提醒行为保持现状；处理结果本身不触发主动通知。

## 4. 崩溃与外部修改

| 中断位置 | 恢复行为 |
|---|---|
| 模型返回、结果接受事务提交前 | 可能重新生成；不承诺 LLM 请求恰好一次 |
| 接受事务提交后、文件写前 | 取已接受结果继续安装；不重新生成 |
| 临时文件 flush 后、最终文件安装前 | `.tmp` 不被读取 / Git 收录；用相同结果重新安装 |
| 最终文件安装后、written 回执前 | 精确比对既有文件，补 written 回执 |
| written 后、Git 提交失败 | 保留文件，自动补做本地提交确认 |
| Git 提交后、published 回执前 | HEAD 核对成功后补 published 回执，不重复生成结果 |
| 已 published 的文件被删除或修改 | 不拿 SQLite 旧缓存自动覆盖；archive 内部入口拒绝读取旧投影；文件完整后重新重放，宿主接线仍待完成 |

真实强杀可能遗留忽略的临时文件；本批没有后台清理策略。测试使用隔离目录并在完成后删除。当前实测是本机进程崩溃恢复；Windows 目录 fsync 不支持，不能由此宣布跨平台掉电一致性通过。

源信息可能在结果接受后再变化。因此“存档已发布”绝不直接变成“可用认识”；M2 的读取 / 派生视图必须核对依赖和修订状态，不能从旧结果恢复已撤回的结论。只有灵魂 Git 也不能重建全部原始对话或尚未发布的工作，备份须分别覆盖来源、待交付结果和灵魂。

semantic-v1 的权威存档重放规则见[语义协议 §5](ADAPTIVE_MEMORY_SEMANTICS.md#5-权威文件与重建)。投影 schema 2 不再把记录外键绑定本机发件箱，完整灵魂文件可在新数据库恢复历史；它不会伪造发件箱、任务完成或 Git 发布回执。当前来源失效不妨碍恢复历史，但会阻止相关认识进入可用结果。已见文件缺失 / 改变时整个语义入口报错；没有尾部见证的新库必须依赖完整备份的检查点检测尾部丢失。

## 5. 防止绕过语义门禁

普通笔记召回与全文索引文档枚举排除 `QuetzalMemory/Adaptive/`；旧结构化导入原已排除整个受管目录。新文件不会因为“看起来像 Markdown”被作为自由笔记送入上下文。管理者仍可检查原始存档，这不等同于语义准入。

M1 的 `source-v1` 只登记来源观察，不产生此类文件。当前发布测试使用合成 payload；后续语义处理器必须在 `acceptResult` 前完成自己的 schema、权限与状态验证，不能把传输信封校验误认为语义安全检查。
