# 自适应记忆：结果发布与恢复协议

状态：M1发布协议、M2 / M3语义原型及M4本机备份恢复 / 运行验收已通过；新记忆及研究仍默认关闭，全量质量与规模留M5，真人反馈经确认后置。阶段推送以验证记录为准。实际进展以阶段验证记录为准。目标和边界见[实施计划](ADAPTIVE_MEMORY_PLAN.md)、[行为契约](ADAPTIVE_MEMORY_CONTRACT.md)与[验证记录](ADAPTIVE_MEMORY_PROGRESS.md)。

## 1. 权威边界

- 原始发言和消息状态仍在既有 SQLite；不为本协议复制完整对话到灵魂 Git。
- 未交付的生成结果存于同一 SQLite 的持久发件箱；任务完成与结果入箱同事务，不依赖模型再次生成来恢复。
- 完整结果文件位于私有灵魂 `notes/QuetzalMemory/Adaptive/<任务 UUID>.md`。文件是处理结果存档，不是事实确认；后续语义认识及其修订由有版本的 payload 表达。
- Git 是文件的版本历史；SQLite 的发布状态是恢复回执。索引和图仍为派生视图。文件落盘、本地 Git 提交、远端同步、语义可用是四种不同状态。

路径符合灵魂规范 v14 的既有 Markdown 笔记目录，不增加顶层目录、不改变固定文件格式，因此不提升灵魂规范版本。SQLite 自适应表从 schema 1 原子升级为 2；未知版本或不同 agent 拒绝打开。M4 验收当前格式的备份恢复；按2026-10-28确认的开发阶段范围，不要求旧程序降级后读取新格式。

## 2. 最小传输信封

Markdown 内使用单行 JSON 代码块，包含：

| 字段 | 含义 |
|---|---|
| `format` | 新写入 `quetzal-adaptive-result-v2`，可读取 v1；未知版本拒绝解析 |
| `id` | 创建该结果的任务 UUID v4；也是不可变文件名 |
| `agent` | 所属灵魂身份；必须与当前 agent 一致 |
| `processor` | 处理器版本，如测试处理器；不表示可信级别 |
| `createdAt` | 中心接受结果的时间；不代替事件发生时间 |
| `inputs` | 1～100 个不重复来源引用 `{id, revision, hash}` |
| `payload` | `{schema, data}`；语义处理器自己校验具体 schema |

整个 JSON 至多 256 KiB，来源 hash 为完整快照 SHA-256。`revision` 是中心本机来源版本，不是跨身体统一计数；重建或跨身体匹配必须以 agent、来源 ID 和 hash 核对，不能拿不同数据库的 revision 作全局先后比较。M2 阶段内已有 [semantic-v2 格式与依赖计算库](ADAPTIVE_MEMORY_SEMANTICS.md)，后台已受控接入，受控前台语义查询已接入，但完整验收尚未完成；未知 payload 只能检查存档，不能进入上下文。

v2 增加显式跨语境关系指向，外层信封也升为 result-v2，使旧宿主在解析时拒绝新文件，而非忽略不认识的 payload 后继续使用旧认识。新程序仍读取原 v1 文件与摘要，不原地迁移历史；新语义不得包装成旧外层，v1 语义不得携带新 references 字段。该内部数据协议升级不改变灵魂规范 v14 的固定目录 / Markdown 笔记格式，也不改变投影表 schema。以上为已有实现，不构成后续必须继续兼容所有旧格式的承诺；旧版混跑与跨格式部署回滚不再列为 M4 门禁。

同一任务只接受一次结果。修改认识应产生后续结果并保留依赖及修订关系，不覆盖旧文件；语义库已实现记录修订与旧版本依赖失效，模型提案和重评已受控接入，但语义质量尚未通过门禁；权威文件重建已有内部库与合成恢复测试，宿主生命周期已接线，完整备份恢复仍待 M4。

## 3. 四个持久阶段

1. **接受结果。** 在 `BEGIN IMMEDIATE` 内检查任务租约令牌、未取消、租约未过期、主要来源版本与全部输入的版本 / hash；结果入 `adaptive_publications`，处理回执与任务 done 一起提交。可信宿主可提供语义投影安装器，与上述写入同事务；返回拒绝或抛异常均回滚全部写入。任一步失败整体回滚。完成回执只说明处理过，不确认正文为真。
2. **安装文件。** 固定主机在后台、灵魂写锁内运行；写同目录随机 `.tmp`，flush 文件，再以不可替换的硬链接原子安装最终名，删除临时名并 flush 目录。同名相同内容只补回执，不重写；同名不同内容、父目录链接、非法文件或摘要不符拒绝覆盖。
3. **记录文件完成。** 发件箱 `pending → written`。此时文件完整，但还不能宣称进入版本历史；文件写入失败每 30 秒重试，最多 5 次，冲突立即失败。只保存错误代码，不保存可能带正文的异常信息。
4. **确认本地 Git。** 复用基座的灵魂提交 / 同步入口，再逐个读取 `HEAD:<路径>`，只有与发件箱预期文件完全一致才 `written → published`。Git 失败保留 written，30 秒后补做，最多 5 次转 failed。重启继续这个阶段，不重新调用生成器。

宿主每轮最多安装 5 份、提交确认 5 份，分别检查启用状态、固定主机身份和急停。Git 异步执行，不在前台查询等待；文件安装仍为同步磁盘操作，其负载与延迟须另测。关闭或急停后不启动下一发布阶段；已进入 Git 的操作不假装可以回滚或立即中断。

`memory.adaptive.status` 的 `queue.publications` 返回 pending / written / published / failed 数量；语义任务 done 可以同时有 pending 或 written 的交付记录，不能据 done 判断持久化全部完成。目前没有发布失败的 UI 重试入口，属于 M4 运维待办；不通过无限重试掩盖失败。

本地 published 不证明远端已同步。远端仍由现有灵魂同步机制负责，状态见既有同步界面；跨重启后的远端恢复与完整备份必须分别验收。原有同步故障提醒行为保持现状；处理结果本身不触发主动通知。

## 4. 崩溃与外部修改

| 中断位置 | 恢复行为 |
|---|---|
| 模型返回、结果接受事务提交前 | 可能重新生成；不承诺 LLM 请求恰好一次 |
| 接受事务提交后、文件写前 | 取已接受结果继续安装；不重新生成 |
| 临时文件 flush 后、最终文件安装前 | `.tmp` 不被读取 / Git 收录；用相同结果重新安装 |
| 最终文件安装后、written 回执前 | 精确比对既有文件，补 written 回执 |
| written 后、Git 提交失败 | 保留文件，自动补做本地提交确认 |
| Git 提交后、published 回执前 | HEAD 核对成功后补 published 回执，不重复生成结果 |
| 已 published 的文件被删除或修改 | 不拿 SQLite 旧缓存自动覆盖；archive 内部入口拒绝读取旧投影；文件完整后重新重放；后台和已接入的读取入口均执行核查 |

真实强杀可能遗留忽略的临时文件；本批没有后台清理策略。测试使用隔离目录并在完成后删除。当前实测是本机进程崩溃恢复；Windows 目录 fsync 不支持，不能由此宣布跨平台掉电一致性通过。

源信息可能在结果接受后再变化。因此“存档已发布”绝不直接变成“可用认识”；M2 的读取 / 派生视图必须核对依赖和修订状态，不能从旧结果恢复已撤回的结论。只有灵魂 Git 也不能重建全部原始对话或尚未发布的工作，备份须分别覆盖来源、待交付结果和灵魂。

semantic-v1 / v2 的权威存档重放规则见[语义协议 §5](ADAPTIVE_MEMORY_SEMANTICS.md#5-权威文件与重建)。投影 schema 2 不再把记录外键绑定本机发件箱，完整灵魂文件可在新数据库恢复历史；它不会伪造发件箱、任务完成或 Git 发布回执。当前来源失效不妨碍恢复历史，但会阻止相关认识进入可用结果。重复读取可在完整权威内容及实际投影摘要均一致时复用已验证投影；文件核对、来源核对不跳过，详细规则见语义协议 §5。已见文件缺失 / 改变时整个语义入口报错；没有尾部见证的新库必须依赖完整备份的检查点检测尾部丢失。

M4收尾将重建改为流式权威结果生成器、SQLite临时暂存表及按代次游标重放；不在JS中保存全部文件正文或排序全图。增量接受通过索引点读所需当前引用，局部patch、回执、发件箱与索引仍同事务。派生索引可重建，不改变结果信封或灵魂规范。每次入口仍核对完整权威文件 / 发件箱和投影摘要，保留中段修改与缺失检测，因此仍有随历史增长的全量I/O；本轮只去掉全量正文物化与全图LLM输入，进一步完整性调度优化须另验。

## 5. 防止绕过语义门禁

普通笔记召回与全文索引文档枚举排除 `QuetzalMemory/Adaptive/`；旧结构化导入原已排除整个受管目录。新文件不会因为“看起来像 Markdown”被作为自由笔记送入上下文。管理者仍可检查原始存档，这不等同于语义准入。

M1 的 `source-v1` 只登记来源观察，不产生此类文件。发布协议的确定性测试使用合成 payload；语义处理器必须在 `acceptResult` 前完成自己的 schema、权限与状态验证，不能把传输信封校验误认为语义安全检查。

## 6. 本机工具读取凭据（M2）

`tool_calls.reading` 是与完整工具记录同一行保存的可空 JSON 字段；store 启动按现有补列模式自动增加，旧行保持 null，不伪造历史来源。它与自适应图 / 队列 schema 独立，也不改变灵魂规范。凭据含格式版本1、agent / body / conv / 工具名、脱敏结果摘要、最多1000个来源 ID / hash 与200个文档标识 / 摘要。并发捕获用 Node 内置 AsyncLocalStorage 隔离；一次捕获观察到矛盾版本或超限时 checked=false，不将其视为有效证明。

凭据与 result 一起保存和淘汰；记录写入失败时不能仅靠内存中的工具文字继续冒充已核查结果。模型准备和工具回查验证作用域、结果摘要及当前来源 / 文件，重建读取视图但不改原 result。原文件 hash / 内容变化或不可访问时旧派生正文不输出；无凭据旧记录要求重新读取。管理者 tool.detail 仍可看到历史原始执行记录及可选 reading，这不是当前语义准入接口。

这些本机记录不参与复制状态或灵魂 Git；既有 tool.detail 的认证远端按需查看仍可返回它们。其他身体不能把本机凭据直接当自己的当前读取证明。重开数据库的持久化已有合成验证，不等于进程强杀、跨身体或完整备份恢复验收。降级程序可以读取旧列，但不会生成新凭据；返回新版本后，无凭据读取仍需重新取得资料，不保证降级期间的纠正行为。

## 本机记忆备份（M4）

控制台「记忆 → 核心 → 对话记忆 → 记忆备份」调用管理接口，在 `QUETZAL_HOME/data/memory-backups/<UUID>` 创建 `quetzal-memory-backup-v1` 清单和文件副本：

- `data/quetzal.db` 使用 SQLite VACUUM INTO，包含原话、来源 / 回答凭据、任务、修订投影与完整性见证，以及已接受但未发布的结果；不直接复制活跃 WAL 文件。
- `soul/` 包含完整工作树、未提交材料、冲突副本和 `.git` 历史。
- 本机存在的 `data/uploads/`、`data/media/`、`data/from-bodies/`、`data/canvas-runs/` 和 `data/restorations/` 文件副本；不抓取离线身体或外部工作区的文件。

运行配置、供应商 / 设备密钥、保密库、自造工具实现、组件 / 向量缓存和日志不在此记忆备份范围内；备份内容本身仍是私人数据，不承诺对对话或灵魂正文进行脱敏。保存在原设备的副本不能抵御整台设备损坏，需要另存到其他存储。现已提供离线 `quetzal restore` 命令，完整多身体恢复验收仍未完成。

本机正常写入在 Git 队列和灵魂锁内以同步回调冻结，比较源文件集合 / 摘要及 SQLite data_version 拒绝观察到的外部变化。不是跨设备原子快照，也不支持多个 runtime 共用家目录；外部编辑器 / 工具不受进程锁约束，不能据此承诺任意外部并发写入的一致性。较大备份可能暂停本机处理，用户主动在空闲时创建；后台普通增量不触发此过程。

清单含 agent、来源身体、程序版本、捕获时间、文件长度与 SHA-256；保留完整数据库格式而非只凭程序版本假定兼容。文件与数据库校验通过后才返回成功；正常失败清理新目录，崩溃遗留 partial 不显示为完成。校验不执行 Git 或脚本、不改当前记忆，也不是来源认证或语义质量证明。恢复必须操作独立副本，不能在备份原件上运行迁移 / 重建。

需求方于2026-10-28确认：恢复时保留全部历史，对后续发言采用新的身体身份，通过正常控制台配对接回同一 agent 并指定记忆中心。历史消息编号不重写，避免旧备份恢复为同名身体后重用已发出的编号。尚存其他身体 / 远端的新纠正须继续追回，不能通过强推让全网倒退。本决策已获授权，离线恢复入口已实现，完整多身体试验仍待完成。

同日进一步确认：恢复面向当前数据格式和运行时；实际旧开发 / 测试数据按需用一次性离线脚本转换副本，不建设自动兼容任意旧备份的长期分支。备份清单中的 runtime 字符串只是记录，不能代替文件、数据格式及完整性核查。未知格式应明确拒绝，原备份保持不变；已有 v1 读取等兼容实现目前仍在，未在本次文档调整中删除。

当前离线恢复流程将历史与运行状态分开：原话、修订、证据依赖、已接受结果和附件接续保存；新身体重新生成身份与密钥、配置连接及记忆中心。旧提醒、未完成行动和续跑状态只保留历史，不因导入自动执行；记忆内部待发布结果可以按现行发布协议接续。完整 SQLite 备份仍含这些运行状态，不能跳过恢复命令，直接复制成新家目录启动。


### 离线恢复命令

`quetzal restore --from <备份文件夹> --home <尚不存在的新家目录>` 调用随包运行基座的 `--restore-memory` 离线入口；Windows 调用已安装版本。命令在加载运行配置、打开正常存储及启动网关前分流，不注册或切换现有守护服务。备份文件夹可改名；本机备份管理仍要求 UUID 与清单一致。拒绝目标已存在、目标位于备份内、文件损坏、未知清单、未迁移的来源编号及未知认识数据版本。

恢复先校验、复制并重算摘要；保留数据库中的原话、时间线、会话、工具与回答凭据、认识修订、发布回执和其他历史表。完整 kv 另存到 `data/restorations/<UUID>.json`，新身体只保留编号迁移标记、项目、人格、记忆使用统计和 PRIME 历史 / 已学标记；旧提醒、轮次、子 agent、连接与临时缓存不进入执行状态。运行中的记忆任务释放旧租约，已取消与失败任务不自动复活，待发布结果保留并经现有存档核查。再次备份包含先前的恢复状态存档。

新身体名使用随机后缀，避开备份已知的消息 / 时间线编号段和身体登记；该检查不承诺发现备份之外的全部身体。UUID 使用现有 manual 来源，避免在同一设备启动时变回旧设备 UUID。新配置暂停自主心跳、关闭记忆处理和局域网发现，配对 / 模型 / 密钥不从旧备份继承；同步地址按运行时默认值处理，没有旧绑定凭据，不会自动接入旧网状连接。管理员经正常控制台配对后选定记忆中心并启用所需功能。

历史附件的持久 JSON 不改写，来源 hash 保持；消息读取视图按 rel 定位新家目录 uploads，离线身体 / 外部工作区原本缺失的文件不会凭空恢复。普通失败清理本次新建目标；进程中断可能留下 `.restore-incomplete`，正常启动在加载配置前拒绝这种目录，应从原备份恢复到另一个新目录。未提供原地覆盖、任意旧版自动迁移或图形导入入口。文件与目录刷盘采用现有平台规则，尚不宣称所有平台的掉电验收。
