## 交付范围

正常对话来源自动进入记忆中心，后台整理带来源和版本的认识，支持歧义、修订、依赖失效及研究；读取通过原文 / 词面 / 向量路径回到实际对话。多身体共享同一个agent，由指定中心处理；消息复制、认识发布、断线补做、自动组件准备、备份恢复均沿现有产品入口运行，不要求日常手改代码或数据库。

保留当前开关和行为：研究不强行默认开启；关联仅在当前相关对话谨慎呈现，不新增通知；新记忆启用时事实统一由新路径整理。来源权限、跨agent隔离、已登记版本和不重复执行动作的边界不放宽。前台100ms向量等待及500ms读取截止不扩大，超时降级可能漏召回。既有文档的“全量M5未通过”仍是事实，不能解释为这一试用版本不能启动。

交付在 `origin/feature/adaptive-memory`，不合并main、不发布npm / 应用商店。开发者按[项目快速开始](../QUICK_START.md)及[runtime运行说明](../../runtime/docs/README.md)准备现有依赖，运行 `npm run build --prefix runtime`；网页控制台按console文档执行 `flutter pub get` 和 `flutter build web`。构建产物分别位于runtime/dist及console/build/web，不提交到Git。


## 分叉后代码审查待修复项（2026-10-29）

以下问题在 `f5bda1d..65d142c` 只读审查中发现，均**尚未修复**。它们不改变既有正式评测成绩，也不应被视为已通过的交付保证。审查时选定187项测试及runtime类型检查通过，但未覆盖下述问题；未重跑真实模型、完整UI或跨平台矩阵。

### P1：内部生成内容可能成为独立证据

- **位置与成因**：`runtime/src/memory/adaptive-worker.ts` 只跳过 `agent`，而 `session_compact` 摘要及子agent报告等内部内容使用 `ambient`；`adaptive-proposal.ts` 的来源投影不包含渠道，`adaptive-evidence.ts` 将 `ambient` 接受为证据根。
- **复现与影响**：隔离合成测试中，仅写入 `ambient` / `摘要` 即可生成一条 `supported` 认识，无需原始用户证据。摘要可能固化误解，原始材料后续纠正也未必能使只依赖摘要的认识失效。此结果证明准入漏洞，不表示每次模型调用都会生成错误认识。
- **待验证的完成条件**：区分内部生成消息与真实环境输入，确保内部摘要、交接和子agent报告不能作为独立来源根；检查已有派生认识及研究、重评路径，避免修复只覆盖新增处理。回归应覆盖摘要 / 子agent、正常用户和真实环境输入，并验证原文纠正或撤销不会留下由生成副本自我支撑的认识。

### P1：长会话在上下文裁剪前超过来源上限

- **位置与成因**：`runtime/src/mind/context.ts` 的 `historyReading` 在 `manager.prepare` 裁剪前合并历史、系统、工具和语义来源；`adaptive.ts` 的 `withAdaptiveSources` 还递归展开回答依赖，超过1000条即报错。
- **复现与影响**：隔离合成测试中，当前会话1000条消息加其他会话一条来源，即使模型窗口足够大，也在模型请求前报“回答来源展开超过工作上限”。自动摘要尚未执行，后续回复可能持续失败；回答依赖展开也可能提前触发上限。
- **待验证的完成条件**：以有界方式选择和核查真正进入上下文的历史及依赖，保留版本、纠正和回答来源约束；不得仅提高上限或静默将未核查内容当作有效证据。回归覆盖长会话、跨会话来源、回答依赖、来源变化与摘要重建，确认正常回复且不复用失效材料。

### P2：控制台漏报发布失败

- **位置与成因**：`console/lib/pages/adaptive_memory.dart` 的 `adaptiveStatusLabel` 只统计处理队列 `counts`，未显示 `publications.failed`；发布文件或Git提交失败最终会保留失败状态，现有处理任务重试按钮不修复发布失败。
- **影响**：处理队列空闲时，页面可能显示“当前未见待处理任务”，即使认识或纠正尚未成功发布。原话仍保留，但不能据此声称发布或跨身体同步完成。
- **待验证的完成条件**：状态明确区分处理与发布失败，不重复统计同一发布队列；回归覆盖失败、待发布、正常空闲及卫星状态，并准确说明现有重试能力。

### P2：宿主向量验证未持续推进分页

- **位置与成因**：`runtime/tool/adaptive-retrieval-probe/host.ts` 设置忙碌以阻止后台刷新，只调用一次 `refreshAdaptiveRetrieval` 后便等待30条索引就绪；现在每次刷新只推进有界批次。
- **复现与影响**：隔离合成复现中，30个候选首次刷新只送出16个，扫描未完成；脚本没有继续推进，会等待超时，无法验证后续真实宿主检索。
- **待验证的完成条件**：验证脚本按分页协议推进至完整扫描与索引就绪，仍保留超时及失败证据；针对多页候选回归，确认所有候选完成后才执行查询。

### P2：多身体向量验证比较了不同含义的摘要

- **位置与成因**：`runtime/tool/adaptive-retrieval-probe/multibody.ts` 把 `retrieval.snapshot` 与 `retrievalExpected` 直接比较；前者是最近批次摘要，后者是完整候选清单摘要。现有 `retrievalSnapshotReady` 已能核对完整清单、扫描及状态。
- **影响**：正常分页索引可能被误判为失败，阻断多身体真实向量工程验证；这本身不证明产品检索失败。
- **待验证的完成条件**：改用完整清单就绪核查，回归覆盖完整且有效的多批次、缺页及清单不匹配；重新运行该验证时如实记录真实组件、替身模型与未覆盖范围。
