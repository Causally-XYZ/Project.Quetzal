## 交付范围

正常对话来源自动进入记忆中心，后台整理带来源和版本的认识，支持歧义、修订、依赖失效及研究；读取通过原文 / 词面 / 向量路径回到实际对话。多身体共享同一个agent，由指定中心处理；消息复制、认识发布、断线补做、自动组件准备、备份恢复均沿现有产品入口运行，不要求日常手改代码或数据库。

保留当前开关和行为：研究不强行默认开启；关联仅在当前相关对话谨慎呈现，不新增通知；新记忆启用时事实统一由新路径整理。来源权限、跨agent隔离、已登记版本和不重复执行动作的边界不放宽。前台100ms向量等待及500ms读取截止不扩大，超时降级可能漏召回。既有文档的“全量M5未通过”仍是事实，不能解释为这一试用版本不能启动。

## 获取、运行与配置

交付在 `origin/feature/adaptive-memory`，不合并main、不发布npm / 应用商店。开发者按[项目快速开始](../QUICK_START.md)及[runtime运行说明](../../runtime/docs/README.md)准备现有依赖，运行 `npm run build --prefix runtime`；网页控制台按console文档执行 `flutter pub get` 和 `flutter build web`。构建产物分别位于runtime/dist及console/build/web，不提交到Git。

运行当前本地构建时，从仓库根执行以下命令，先将变量设为仓库外的专用运行目录（实际路径不入库）：

```sh
: "${QUETZAL_TRIAL_HOME:?请先设置仓库外的专用运行目录}"
QUETZAL_HOME="$QUETZAL_TRIAL_HOME" QUETZAL_WEB_DIR="$PWD/console/build/web" node runtime/dist/main.cjs
```

平台适配器使用现有配置或QUETZAL_ADAPTER；不填时沿基座默认身体。打开启动日志显示的本机控制台地址，在控制台配置模型、开启自适应记忆并指定记忆中心。第二身体通过现有设备配对接入同一agent；每具身体使用独立运行目录和端口。已安装用户继续使用现有启动 / 配置 / 备份管理入口；上面是开发构建启动说明，不是用户日常运维要求。不要通过公开npm安装命令假定已取得本分支尚未发布的代码。

## 验证与边界

沿用代码候选的类型检查、完整runtime构建及107项相关回归（阶段记录§7.38）；真实E5的1001候选组合可索引、查询、更新与重启。历史真实模型多身体、代理半年生活和控制台交互证据见M2–M4及M5阶段记录，不重复声称本次重新完成它们。本次额外只做关键链路冒烟，结果见阶段记录§7.40。

后续已修复分叉后代码审查发现的5项工程问题，并消除万条向量查询中逐分块 `setImmediate` 与 `N+1` JSON/SHA-256重算瓶颈，将每个候选的多分块向量展平为连续 `Float32Array`：在真实E5查询下，10000条已索引候选（单块与双块共20000分块）的worker查询耗时由超时降级降至约21.85–50.30ms（4/4均在100ms预算内返回Top-1000），宿主端到端查询耗时约201.03–245.97ms（在500ms截止内稳定返回材料）；批次清单提交遇SQLite写锁支持原地退避恢复或仅拒绝当前批次重发，不再销毁已加载的worker。正式v2仅10条完整核读，9条合格、1条失败，另1条中断、139条未执行。因此本版不宣称95%准确率、任意历史规模可用或生产级质量通过。生成模型仍可能误解时间范围、指代或因果；来源 / 版本一致不等于语义必然正确。

## 分叉后代码审查项修复与验证（2026-10-29）

以下问题在 `f5bda1d..65d142c` 只读审查中发现，现已全部修复并通过回归验证；它们不改变既有正式评测成绩，也不代替全量150序列或跨平台矩阵验收。

### P1：内部生成内容可能成为独立证据（已修复）

- **位置与成因**：`runtime/src/memory/adaptive-worker.ts` 原先只跳过 `agent`，而 `session_compact` 摘要及子agent报告等内部内容使用 `ambient`；`adaptive-proposal.ts` 的来源投影不包含渠道，`adaptive-evidence.ts` 将所有 `ambient` 接受为证据根。
- **修复与验证**：在 `adaptive-evidence.ts` 定义统一的 `isEvidenceSource` 与 `INTERNAL_AMBIENT_CHANNELS`（`摘要 / 交接 / 续做 / 子agent / 灵魂同步 / 换身体`），贯穿证据求值、整合任务、工作集、重评、研究、查询与来源修订读取。回归测试（`adaptive-source-edit.test.ts`、`adaptive-research.test.ts`）验证内部 `ambient` 消息直接完成回执而不调用模型、不成为独立证据根，既有引用内部摘要的认识降为 `unsupported` 且不进入后续整合或研究，而真实用户消息与 `ambient/语音` 照常整合。

### P1：长会话在上下文裁剪前超过来源上限（已修复）

- **位置与成因**：`runtime/src/mind/context.ts` 的 `historyReading` 在 `manager.prepare` 裁剪前合并历史、系统、工具和语义来源；`adaptive.ts` 的 `withAdaptiveSources` 还递归展开回答依赖，超过1000条即报错。
- **修复与验证**：`historyReading` 在窗口裁剪前按从新到旧保留单次可核查上限及窗口 / 摘要输入预算内的历史，合并跨会话等来源超限时自动放弃继承旧摘要；`withAdaptiveSources` 对展开后超出1000条上限的单条旧助手回答保守标记为 `changed`（输出 `ANSWER_CHANGED` 占位），不截断后冒充有效，也不抛错阻断当前对话。回归测试（`adaptive-history.test.ts`）覆盖1000条会话消息加跨会话来源与超限回答依赖，验证1M与64K窗口下均正常回复、自动摘要且不泄漏未核查或失效正文。

### P2：控制台漏报发布失败（已修复）

- **位置与成因**：`console/lib/pages/adaptive_memory.dart` 的 `adaptiveStatusLabel` 原先只统计处理队列 `counts`，未显示 `publications.failed` 与待发布项。
- **修复与验证**：`adaptiveStatusLabel` 读取单一 `publications` 统计（不跨队列重复累加），明确区分处理失败、认识发布失败及待写入/提交灵魂仓库的数量，并说明重试按钮仅针对处理任务。`console/test/adaptive_memory_test.dart` 覆盖仅发布失败、处理与发布同时失败、待发布、正常空闲及卫星状态。

### P2：宿主向量验证未持续推进分页（已修复）

- **位置与成因**：`runtime/tool/adaptive-retrieval-probe/host.ts` 设置忙碌以阻止后台刷新，只调用一次 `refreshAdaptiveRetrieval` 后便等待30条索引就绪，而每次刷新只推进有界批次。
- **修复与验证**：`settled` 在手动模式下持续调用 `refreshAdaptiveRetrieval` 直至 `hostCurrent` 与 worker 索引同时就绪，并分页遍历 `candidatePage`。本机实跑 `host.ts` 11项检查全部通过（词面 hit@6 8/14，混合 14/14，P95 47.21ms）。

### P2：多身体向量验证比较了不同含义的摘要（已修复）

- **位置与成因**：`runtime/tool/adaptive-retrieval-probe/multibody.ts` 把最近批次摘要 `retrieval.snapshot` 与完整候选清单摘要 `retrievalExpected` 直接比较。
- **修复与验证**：改用 `retrievalSnapshotReady(cp.preAnswer.center)` 核对完整候选清单、扫描完成状态与批次元数据。本机实跑 `multibody.ts`（真实E5组件、双身体WebRTC与自动Git发布、生成模型替身）两条轨迹共5个检查点全部通过（读取耗时 8.93–14.81ms）。
