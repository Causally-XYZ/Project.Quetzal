# Quetzal 的目的、原则与取舍

本文整理已对齐的产品意图和工程原则，供设计、开发与评审共同使用。它说明为什么这样做，不把目标写成已经实现的保证。当前模块结构见[架构](ARCHITECTURE.md)，记忆的具体行为与覆盖边界见[行为契约](engine/ADAPTIVE_MEMORY_CONTRACT.md)和[实现总览](engine/ADAPTIVE_MEMORY.md)。

## 1. 产品究竟提供什么

Quetzal 是通用的 agent 运行基座。模型提供理解与生成能力，基座提供持续存在所需的身份、身体、记忆、行动、节律与权限。更换模型、设备或交互入口，不应要求用户重新建立全部关系与上下文。agent 的名字和人格来自私有数据，不写死在产品中。

“生命”“灵魂”“身体”“心脏”是产品与模块的命名，不是意识或人格真实性的科学断言。自主活动也不意味着无限权限：能力由适配器提供，行动受授权、审计、停止机制和实际资源限制。控制台帮助用户理解和控制这些行为，日常使用不要求操作源码、数据库或 Git。

身份与记忆由部署者持有，灵魂仓库私有、格式可读、同步自动完成。运行数据、凭据与公开程序分离；模型服务仍会接收调用所需材料，“私有仓库”不等于全部计算都在本机。身体、控制台、同步服务和模型供应商各自承担有限职责，不能把服务便利性当成扩大信任范围的理由。

## 2. 记忆从什么问题出发

用户不是完整记录生活的传感器。他们可能几个月才再次提起一个人，也可能不告诉系统决定性的事实。原话可能含代词、别名、转述、小说、假设、口误和转写错误。一段话能同时属于多个主题，重要主题事前无法穷举。

所以目标是逐渐理解对用户有意义的人、事、物和主题，在合适的时候帮助回顾、关联、思考和发现。目标不是把每句话变成确定事实，也不是生成尽可能大的知识图谱。图、向量、SQL、规则和模型都是表达、寻找与修正认识的手段，应以实际帮助和代价判断价值。

需要持续区分：

| 区分 | 为什么必要 |
|---|---|
| 原始发言、系统理解、进一步推测 | 确实有人这样说，不代表内容或解释正确；模型复述不是新证据 |
| 对象提及、候选身份、已绑定身份 | 同名和相似表达不能直接合并人或物；局部纠正不应变成全局别名替换 |
| 现实、故事、假设与未知语境 | 可以谈论或创作另一个语境中的对象，不能借此混同身份或事实依据 |
| 记录时间、事件时间、有效期、修订时间 | 改正过去与状态后来改变不同；历史纠正不能自动证明现在仍成立 |
| 相关、支持、反证、必要假设 | 共现和可组合不等于因果、真实创作动机或充分证明 |
| 未知、未召回、明确否定 | 不完整记录和有界检索不能证明事情没有发生 |

## 3. 模型与工程各负责什么

LLM 适合提议消歧、主题、命题、时间范围、候选关系和解释，也适合寻找反例或需要澄清的问题。这些判断可以修改，不靠模型自报置信度授予“事实”身份。

宿主明确管理来源身份、访问范围、版本、引用、任务生命周期、事务、发布与取消。工程校验可以拒绝过期提案、越权来源和悬空引用；它不能证明自然语言命题是真的，也不能保证模型找到了所有隐含依赖。`supported` 表示记录的依据规则成立，不表示世界真相已经核实。

对于可定义的程序性质，应使用类型、测试、契约或适当的形式化方法；对于语义有用性、消歧和研究收益，需要实际轨迹与独立核读。形式化结论依赖建模和前提正确，不能把错误原话变真。现阶段未引入通用定理证明器或约束求解器作为生产记忆裁判；相关探索和分歧保留在[第一性原理复审](engine/ADAPTIVE_MEMORY_FIRST_PRINCIPLES_REVIEW.md)。

## 4. 修正比维持表面一致更重要

用户纠正出现后，先辨明对象、命题、语境和时间范围。没有发现与其他仍有效材料的实质冲突时，应接受纠正并调整相关依赖。系统过去反复说过同一句话、同一来源的多个摘要，都不是抵抗纠正的独立证据。

若纠正与仍然适用的其他证据或约束冲突，应保留新说法，指出具体不协调之处，在相关对话中复核；不能悄悄忽略纠正，也不能把任一方写成确定事实。偏好和计划可以改变，不能只因与过去不同就要求用户证明自己。局部变更应尽量保留未受影响的内容；多个独立充分依据中一组失效，不必抹掉仍有独立依据的认识。

系统应减少错误自我强化：派生结果追溯到根来源，循环引用和重复生成不增加独立支持，已知失效内容不能作为新的现行依据。工程保证从正确识别并持久接受的修订开始；识别是否正确、影响范围是否完整，仍是经验问题。

## 5. 以演化轨迹评估可靠性

合理错误可以接受，长期污染和不可修正更值得警惕。观察新信息、用户反馈和重复使用之后，错误是否减少、是否复发、是否扩散到无关主题，是否为了回避错误而不再提供帮助。95% 是已讨论的质量方向，正式评分另有固定分母和分项标准，不是当前成绩或逐条提案准入概率。

“使用越久越可靠”是要检验的目标，不是无条件收敛定理。没有新证据、证据相互依赖、记录严重缺失或现实持续变化时，系统可能无法确定；保留未知或多个解释也是合理结果。重读原文能修正理解，但不会增加独立观测。

验证必须多样且纵向：更换题材、错误机制和人物关系，穿插无关话题，再检验纠正后的相关使用。生活模拟应分开外部世界、角色所知和产品所见；事件系统按约 30% 的记录概率独立掷骰，不为凑齐推理线索而让角色事无巨细地汇报，并包含转写错误、typo 和未被记录的事实。半年代理模拟、移动浏览器视口、工程替身、真实模型和真人反馈分别记录，不能互相冒充。研究讨论是待检验观点，不是测试成绩。

## 6. 探索、呈现与运行边界

- 同一 agent 的全部可访问对话默认可关联，但不扩大来源权限，不把同一 agent 的所有使用者当成同一个人。
- 后台探索可以宽，前台呈现要谨慎。只在当前相关对话中提出有帮助的联系，明确推测，允许没有 insight；新记忆不另发通知或主动开会话。原有心脏和用户授权的提醒另有规则。
- 关系、动机或心理状态的线索不是诊断，也不自动授权联系他人或外部干预。
- 多身体共用一个 agent，由指定身体集中处理记忆；它与自动选举的心脏协调者是两种职责。断线时不能承诺知道其他身体最新的纠正。
- 输入持久化与后台理解分开，前台不等待全图重算。有界候选和必要依据展开优先于全量输入；超限、缺资料和降级应如实表达，未召回不等于不存在。
- 安装组件、重试、同步和恢复应经产品流程自动运行。备份恢复使用新身体身份，保留历史、不重放旧行动；开发期旧数据可按需脚本迁移，不为任意旧版本兼容增加长期负担。

## 7. 如何做工程取舍

先接入真实产品入口验证完整体验，借鉴高质量开源实现；证据足够后再通过对照、消融和重构减少复杂度。不要把扩充评测设施、逐个补提示或形式上的零错误，当作整体可行性的替代。

遇到显著瓶颈或原设计可疑时，回到 WHY / WHAT，允许否定已有实现。已约定可与 Gemini 4 开展多轮讨论：先独立思考，再提供核实后的代码与实验；只发架构和合成案例，记录实际模型和返回状态，保留分歧。不能为了保住既有投入而预设 HOW。

设计契约、实现和证据分别维护。改变产品行为、核心架构或已对齐验收范围需要说明理由和取舍后对齐；一般实现修复不应反复要求用户批准。当前交付优先级已经改为完整可运行试用版，其余工作列入 [backlog](engine/ADAPTIVE_MEMORY_RELEASE.md)，不得把原失败改判为通过，也不自动恢复旧 GOAL 的全部阻塞门槛。
